# DATABASE.md

# Dodo Payments --- Final PostgreSQL Schema

## Purpose

This is the source of truth for the physical PostgreSQL schema. Schema
changes use Goose; application SQL uses sqlc + pgx/v5. Architectural
reasoning belongs in `DESIGN.md`.

## ID Strategy

All application primary and foreign keys use Snowflake-style signed 64-bit integers stored as PostgreSQL `BIGINT` and Go `int64`. Snowflake IDs are roughly time ordered and generated in the application before insert. The generator must handle worker/node uniqueness, same-millisecond sequence exhaustion, and clock rollback.

Raw Snowflake IDs are not exposed directly through the HTTP API. Public IDs use a resource prefix plus a deterministic keyed reversible encoding, for example `inv_<encoded>`, `cus_<encoded>`, and `att_<encoded>`. One application-level `ID_CODEC_SECRET` is used across resources, while the resource type is included as codec context. Prefix/type validation happens before decoding. The encoded public value is never stored or indexed in PostgreSQL; after decoding, queries use the native `BIGINT` ID. Public-ID encoding is obfuscation/representation, not authorization; every business-owned query remains scoped by authenticated `business_id`.

Examples:

```text
DB:  842735982145671168
API: inv_K7xP92Qa
```

```text
GET /invoices/inv_K7xP92Qa
  -> validate inv_
  -> keyed decode with resource context "inv"
  -> 842735982145671168
  -> SELECT ... WHERE id = $1 AND business_id = $2
```

Do not use separate codec secrets per resource. Do not use the codec as an authorization mechanism. Production key rotation/versioning is documented as a production-readiness concern.

## Conventions

Use Snowflake-style 64-bit integer IDs generated by the application. Use
`TIMESTAMPTZ` in UTC. Use `BIGINT` integer cents for money.

Use `VARCHAR + CHECK`, not PostgreSQL ENUM types.

All controlled lifecycle/event values are UPPERCASE across DB, Go, API,
OpenAPI, tests and docs:

-   Invoice: `DRAFT`, `OPEN`, `PAID`, `VOID`, `UNCOLLECTIBLE`
-   Payment: `PROCESSING`, `SUCCEEDED`, `FAILED`, `UNKNOWN`
-   Idempotency: `PROCESSING`, `COMPLETED`
-   Webhook delivery: `PENDING`, `PROCESSING`, `DELIVERED`, `EXHAUSTED`
-   Webhook event: `INVOICE.CREATED`, `INVOICE.PAID`,
    `INVOICE.PAYMENT_FAILED`

Reason/error codes remain lowercase.

### API key secret generation and storage

API-key secrets must be generated from a cryptographically secure random
source. For local provisioning and the take-home demo, generate a 256-bit
(32-byte) secret with OpenSSL:

``` bash
openssl rand -hex 32
```

This returns 64 hexadecimal characters. The generated value is the plaintext
API-key secret and must be shown/provided to the caller only when the key is
created. Do not store or log the plaintext secret.

The API key exposed to a client should contain a globally unique, non-secret
lookup prefix and the generated secret, for example:

``` text
dp_test_<key_prefix>_<secret>
```

The database stores only:

``` text
key_prefix  = non-secret lookup prefix
secret_hash = SHA-256(plaintext secret), encoded as lowercase hexadecimal
```

The SHA-256 digest is 32 bytes and its hexadecimal representation is 64
characters, matching `secret_hash VARCHAR(64)`. SHA-256 is appropriate here
because the API secret is machine-generated with 256 bits of cryptographic
randomness; this is not a password-hashing design.

Authentication flow:

``` text
Authorization: Bearer dp_test_<key_prefix>_<secret>
        |
        +--> parse key_prefix and secret
        +--> lookup api_keys by key_prefix
        +--> reject when revoked_at IS NOT NULL
        +--> SHA-256(presented secret)
        +--> constant-time comparison with stored secret_hash
        +--> authenticate the associated business_id
```

`ID_CODEC_SECRET` is unrelated to API-key authentication. It is used only for
public resource-ID encoding/decoding. Never reuse it as an API-key secret.

### Development/demo seed data

The assignment requires API-key authentication but does not require API-key
management CRUD endpoints. Local startup therefore bootstraps one demo
Business and one API key belonging to that Business.

Schema creation remains in Goose migrations. Demo data provisioning is a
separate seed/bootstrap step and must be idempotent so repeated
`docker compose up` executions do not create duplicate businesses or API
keys.

For the demo, provision the API-key secret from configuration. A developer may
generate the value with:

``` bash
openssl rand -hex 32
```

Only the non-secret `key_prefix` and SHA-256 hash of the configured secret are
persisted in `api_keys`. The plaintext secret is never inserted into the
database. Production API-key creation, rotation, and lifecycle-management APIs
are intentionally outside the scope of this assignment.

## idempotency_keys

  Column            Type             Null Notes
  ----------------- -------------- ------ ---------------------------
  id                BIGINT               No PK
  business_id       BIGINT               No FK businesses
  idempotency_key   VARCHAR(255)       No Client header
  request_hash      VARCHAR(64)        No SHA-256 canonical request
  status            VARCHAR(32)        No PROCESSING/COMPLETED
  response_status   INTEGER           Yes Final HTTP status
  response_body     JSONB             Yes Final response
  created_at        TIMESTAMPTZ        No DEFAULT NOW()
  updated_at        TIMESTAMPTZ        No DEFAULT NOW()

Constraints:

``` sql
PRIMARY KEY (id)
FOREIGN KEY (business_id) REFERENCES businesses(id)
UNIQUE (business_id, idempotency_key)
CHECK (status IN ('PROCESSING','COMPLETED'))
CHECK (
  (status = 'PROCESSING' AND response_status IS NULL AND response_body IS NULL)
  OR
  (status = 'COMPLETED' AND response_status IS NOT NULL AND response_body IS NOT NULL)
)
```

The UNIQUE constraint provides the idempotency lookup index. The
canonical request fingerprint includes the mock card token, but the raw
token is not stored.

A payment can be `UNKNOWN` while this HTTP operation is `COMPLETED` with
a stored 202 response.

## payment_attempts

  Column               Type             Null Notes
  -------------------- -------------- ------ -------------------------------------
  id                   BIGINT               No PK
  invoice_id           BIGINT               No FK invoices
  idempotency_key_id   BIGINT               No FK idempotency_keys
  status               VARCHAR(32)        No Payment status
  psp_request_id       BIGINT               No Local stable correlation ID
  psp_ref              VARCHAR(255)      Yes PSP ref on confirmed success
  failure_code         VARCHAR(100)      Yes PSP decline code
  failure_reason       TEXT              Yes Controlled local uncertainty reason
  psp_requested_at     TIMESTAMPTZ       Yes PSP call start
  psp_responded_at     TIMESTAMPTZ       Yes Definitive response time
  created_at           TIMESTAMPTZ        No DEFAULT NOW()
  updated_at           TIMESTAMPTZ        No DEFAULT NOW()

Constraints:

``` sql
PRIMARY KEY (id)
FOREIGN KEY (invoice_id) REFERENCES invoices(id)
FOREIGN KEY (idempotency_key_id) REFERENCES idempotency_keys(id)
UNIQUE (idempotency_key_id)
UNIQUE (psp_request_id)
CHECK (status IN ('PROCESSING','SUCCEEDED','FAILED','UNKNOWN'))
```

Critical concurrency invariant:

``` sql
CREATE UNIQUE INDEX uq_payment_attempts_unresolved_invoice
ON payment_attempts (invoice_id)
WHERE status IN ('PROCESSING','UNKNOWN');
```

History index:

``` sql
CREATE INDEX idx_payment_attempts_invoice_created
ON payment_attempts (invoice_id, created_at DESC);
```

Semantics: - `PROCESSING`: external result not safely persisted. -
`SUCCEEDED`: definitive success; `psp_ref` populated. - `FAILED`:
definitive PSP decline; `failure_code` such as `card_declined`. -
`UNKNOWN`: ambiguous result; `failure_reason` such as `psp_timeout` or
`network_error`.

One idempotency operation creates at most one payment attempt. One
invoice has at most one unresolved attempt.

## Payment Transaction Boundary

Claim:

``` text
BEGIN
  scope/validate + short row lock on invoice
  resolve/create idempotency record
  verify invoice is payable
  insert payment_attempt(PROCESSING)
COMMIT
```

Call PSP outside DB transaction.

Finalize:

``` text
BEGIN
  update payment attempt
  transition invoice if required
  create webhook delivery rows
  complete idempotency response
COMMIT
```

Never hold DB locks during PSP HTTP.

If PSP succeeds but the app crashes before persistence, PostgreSQL may
still show `PROCESSING`. That does not prove failure. The
unresolved-attempt constraint blocks another charge. Do not
automatically retry the PSP.

Constraints:

``` sql

CHECK (event_type IN ('INVOICE.CREATED','INVOICE.PAID','INVOICE.PAYMENT_FAILED'))

```

Worker index:

``` sql
CREATE INDEX idx_webhook_deliveries_due
ON webhook_deliveries (next_attempt_at)
WHERE status IN ('PENDING','PROCESSING');
```

### Worker claim/recovery

Use a short `FOR UPDATE SKIP LOCKED` transaction. Claim a due `PENDING`
row by setting `PROCESSING` and setting `next_attempt_at` to a short
claim-expiry time; commit before HTTP.

A `PROCESSING` row whose `next_attempt_at` has passed is a stale claim
and may be reclaimed. This prevents worker crashes from permanently
stranding work without another lease column.

After HTTP: - success → `DELIVERED`, set `delivered_at` - retryable
failure → `PENDING`, increment count, schedule `next_attempt_at` - final
failure → `EXHAUSTED`

Retry schedule: immediate, +1m, +5m, +30m, +2h, +12h; six attempts
total.

## Transactional Webhook Outbox

Insert required webhook delivery rows in the same transaction as the
domain state change.

Example:

``` text
BEGIN
  payment PROCESSING → SUCCEEDED
  invoice OPEN → PAID
  insert INVOICE.PAID deliveries for active endpoints
  complete idempotency response
COMMIT
```

No separate webhook-events table is required. One delivery row per
active endpoint is sufficient for this take-home.

## Card Tokens

There is no `card_tokens` table. Do not persist card number, CVV, expiry
or raw mock token. The token is forwarded to the mock PSP and included
in the canonical idempotency fingerprint.

## API Key Security

Generate cryptographically random API-key secrets. Persist only globally
unique `key_prefix` and SHA-256 secret hash. Never log plaintext.

## Delete Behavior

Do not add broad `ON DELETE CASCADE` for financial/payment records. Use
restrictive FK behavior unless an explicitly approved lifecycle requires
otherwise.

## Public ID Prefixes

Use these API prefixes when the corresponding identifier is exposed:

```text
biz_   business
key_   API-key record
cus_   customer
inv_   invoice
itm_   invoice item
idem_  idempotency record
att_   payment attempt
whe_   webhook endpoint
whd_   webhook delivery
```

The ID generator and public-ID codec are separate responsibilities, preferably `internal/idgen` and `internal/publicid`. `psp_ref` remains the provider's string reference. `psp_request_id` may use a Snowflake `BIGINT` as a local correlation identifier.

## Integrity Boundary

PostgreSQL enforces relationships, customer/business consistency for
invoices, globally unique API-key prefixes, business-scoped idempotency
uniqueness, one attempt per idempotency operation, one unresolved
attempt per invoice, controlled values, positive quantities,
non-negative money and USD-only invoices.

Application logic enforces invoice transition rules, authorization,
total calculation, idempotency hash comparison, PSP interpretation,
finalization behavior and webhook signing/payload behavior.

External PSP side effects cannot be made atomic with PostgreSQL.

## Schema Change Rule

For any new table/column/type/state/index/constraint/relationship:
explain the limitation and proposed change first; after approval update
`DATABASE.md`, Goose migration, sqlc, tests, `DESIGN.md` when reasoning
changes, and OpenAPI when public behavior changes.
